# ADR 0001：用 ABAC 而非 RBAC 做授权模型

- 状态：已接受
- 日期：2026-09-09
- 背景：与 `spring-rbac` 构成对照实验，验证属性化授权的表达力与代价

## 背景

RBAC 的表达力边界在角色爆炸。当"谁能看什么"取决于多个维度组合时
（部门 × 密级 × 地区 × 时间 × 作者），角色数量按笛卡尔积增长：
`ENG_MANAGER_CN`、`ENG_MANAGER_US`、`SALES_VIEWER_CN`……
每加一个维度就翻倍，而每个角色内部仍是黑盒——
从角色名看不出"为什么这个人能看这份文档"。

## 决策

采用 ABAC：决策 = f(主体属性, 资源属性, 环境属性, 动作)。

- 属性来源三方：JWT claims（主体）、业务库经 PIP 回源（资源）、请求上下文（环境）
- 策略 = 作用域 + SpEL 条件 + 效果 + 优先级
- 合并算法 deny-override，无命中默认拒绝

## 理由

1. **维度可扩展**：加一个维度是加一条策略，不是加 N 个角色
2. **例外可表达**：`P-100 非工作时间禁止删除` 能盖住 `P-05 管理员全权`，
   RBAC 里 `ROLE_ADMIN` 是布尔值，没法表达"有权限，但是……"
3. **策略可读**：`subject.clearance >= resource.requiredClearance` 自解释，
   不需要查角色树才知道某人为什么能访问
4. **跨服务一致**：所有域问同一个 PDP，不存在"这个服务忘了校验"的洞

## 代价（明确接受）

| 代价 | 缓解 |
|---|---|
| 判定从 O(1) 查表变 O(n) 求值 | 作用域粗筛 + 表达式缓存 |
| 需要表达式沙箱 | 黑名单 + 类型定位器 + 只读访问器（见 ADR 0002） |
| 需要 PIP 回源，多一次网络调用 | 调用方带全属性时跳过回源；回源失败 fail-closed |
| 属性快照导致变更不实时 | 接受：下次登录生效（见 ADR 0003） |
| "为什么被拒绝"变难排查 | 审计记命中策略 + 前端展示判定轨迹 |

## 备选方案

- **RBAC + 角色条件**：在角色上挂条件，等于把 ABAC 塞进 RBAC 壳子，
  两套心智模型叠加，比纯 ABAC 更难懂
- **ReBAC（关系型，如 Google Zanzibar）**：适合社交图谱类关系授权，
  本项目是"属性匹配"场景，Zanzibar 的元组模型反而绕
- **集成 OPA / Rego**：能力更强，但多一个外部组件和一门新语言（Rego），
  演示项目里不划算（见 ADR 0002）
