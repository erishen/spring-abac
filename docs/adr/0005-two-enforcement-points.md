# ADR 0005：边缘 PEP + 服务内行级过滤，两道闸门

- 状态：已接受
- 日期：2026-09-09

## 背景

网关（PEP）拦在边缘，能判"这个接口能不能碰"，但不知道列表里每一行是什么密级；
业务服务持有数据，能做行级过滤，但每个服务都自己接一遍 PEP 成本太高。

## 决策

两道闸门，问同一个 PDP：

1. **网关 PEP**：JWT 校验 → 映射 (资源类型, 动作, 资源 id) → 问 PDP → PERMIT 才放行
2. **业务服务**：逐行问 PDP 批量接口 → 只放行 `permitted == true` 的行 → 再分页

## 理由

- **策略不会不一致**：两道问的是同一个 PDP，策略改了两边同时生效
- **行级过滤只有业务服务能做**：网关只认得 URL 里的 id，
  不知道列表里第 3 行是 SECRET 第 5 行是 PUBLIC
- **成本可控**：第 2 道用 `/api/decide/batch`，一次问完所有行，
  不是 N 次串行调用

## 为什么不能只留一道

- 只有网关：接口能进但内容全不该看，且直连内部服务就绕过了
- 只有业务服务：每个服务都要实现一遍 PEP（JWT 校验、PDP 调用、熔断、审计），
  必然有的服务做得好有的做得糙

## PDP 不可用时的行为

两道都 **fail-closed**：
- 网关侧熔断打开 → 立刻 403（不让请求卡等 PDP 超时拖垮网关线程池）
- 业务服务侧调用异常 → 抛 `ForbiddenException`

授权系统里"PDP 挂了就放行"是灾难性设计——一次抖动等于全站裸奔。

## 当前简化

业务服务信任网关注入的 `X-Attr-*` 头，前提是"网关是唯一入口"
（内部服务只注册 Eureka，不对外暴露端口）。
零信任环境下应改用内网 mTLS 或业务服务侧校验 JWT。
