# ADR 0004：采用 deny-override 合并算法

- 状态：已接受
- 日期：2026-09-09

## 背景

多条策略同时命中时如何合并？常见算法：

| 算法 | 语义 | 特点 |
|---|---|---|
| deny-override | 任一 DENY 命中即拒绝 | 安全默认，例外可表达 |
| permit-override | 任一 PERMIT 命中即放行 | 宽松，但无法表达例外 |
| first-applicable | 按优先级取第一条命中的 | 结果依赖排序，难推理 |
| only-one-applicable | 命中多于一条即报错 | 严格，配置负担重 |

## 决策

**deny-override + 优先级排序 + 无命中默认拒绝**。

求值顺序按 priority 降序，遇到 DENY 立即短路返回，不再看后面的 PERMIT。

## 理由

1. **能表达例外**：这是选它的核心原因。
   `P-100 非工作时间禁止删除` 能盖住 `P-05 管理员全权`——
   一般规则写宽、例外单独写 DENY，符合安全直觉。
   permit-override 下这条例外根本写不出来。
2. **失败安全**：多写一条 DENY 只会收紧不会放宽，
   配错了是"不能用"而不是"全都能用"
3. **优先级只影响短路顺序**：不是"谁覆盖谁"的复杂语义，心智负担低

## 为什么不是 first-applicable

first-applicable 下，判定结果完全取决于策略排序。
策略数量增长后，"为什么这个人被拒绝"需要人脑跑一遍排序，运维成本高。
deny-override 下只需找**是否存在匹配的 DENY**，可判定性强得多。

## 代价

PERMIT 必须显式写——没有"默认允许"这回事。
新加业务域时如果忘了配 PERMIT 策略，现象是"全都访问不了"。
这是有意为之：宁可配置漏了导致不可用（立刻被发现），
也不要配漏了导致全放行（可能长期不被发现）。
