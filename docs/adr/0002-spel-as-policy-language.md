# ADR 0002：用 SpEL 做策略条件语言

- 状态：已接受
- 日期：2026-09-09

## 背景

策略条件需要一门表达式语言。候选：SpEL（Spring 自带）、MVEL、OGNL、
Groovy、Rego（OPA）、自研 DSL。

## 决策

用 SpEL，配四层沙箱：

1. **正则黑名单**：禁 `T(`、`new `、`getClass`、`\.class`、`ClassLoader`、
   `Runtime`、`ProcessBuilder`、`System.`、`@`、`exec(`
2. **类型定位器抛异常**：`setTypeLocator()` 直接抛错，让 `T(...)` 在解析阶段失败
3. **只读 Map 访问器**：属性不存在返回 `null` 而非抛异常，
   使 `subject.foo == null` 这类条件能正常求值
4. **表达式缓存**：按字符串缓存解析结果，避免每次判定重新解析

## 理由

- **零额外依赖**：Spring 自带，不引入新 jar，也不引入新语言
- **零学习成本**：Java 开发者一眼看懂 `subject.clearance >= resource.requiredClearance`
- **够用**：属性读取、比较、逻辑运算、字符串方法覆盖了授权的全部需求

## 踩过的坑

黑名单最初用子串匹配 `.class`，误杀了 `resource.classification`——
条件里访问资源密级是最常见的写法。改用正则（`Pattern.compile` + 词边界）后解决。
**教训：安全黑名单不能用子串匹配，容易误伤正常业务字段。**

## 备选方案

- **OPA / Rego**：专门的策略引擎，能力更强（部分求值、策略测试框架），
  但多一个外部组件和一门新语言。演示项目里不划算；生产环境若策略量上规模值得迁
- **自研 DSL**：能精确控制能力边界（最安全），但要自己写 parser、错误处理、IDE 支持，
  投入产出比差
- **Groovy / MVEL**：能力太强（可写任意代码），沙箱成本高

## 残余风险

黑名单 + 类型定位器是"堵已知漏洞"，不是"证明安全"。
生产环境应再加：白名单函数表、表达式静态分析、上线前 dry-run 全量策略。
