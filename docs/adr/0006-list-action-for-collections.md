# ADR 0006：集合请求用 LIST 动作，与单条 READ 分开

- 状态：已接受
- 日期：2026-09-09

## 背景

边缘 PEP（网关）只能从 URL 里拿到资源 id。`GET /api/documents/{id}` 能解析出 id，
PDP 可以经 PIP 回源取到完整资源属性再判 READ；但 `GET /api/documents` 是**集合请求**，
没有任何具体资源，属性包是空的。

实现时踩到的坑（真实故障，不是假想）：

```
GET /api/documents  →  PDP 收到 resource = {type: "DOCUMENT", id: null}
                    →  所有形如 resource.classification == 'PUBLIC' 的条件都不命中
                    →  无任何策略命中 → default deny → 403
```

现象很有迷惑性：**admin 能列（6 篇），其他人全是 403**。因为 P-05
（`subject.title == 'admin'`）是纯主体条件，不依赖资源属性；其余策略都引用了 `resource.*`,
在空属性包下全部落空。看起来像"策略配错了"，实际是"问错了问题"。

## 决策

网关对 `GET` 且 URL 中无资源 id 的请求，映射为 **`LIST` 动作**（而非 `READ`），
并补一组只回答"能不能列这个域"的 LIST 策略：

| 策略 | 作用域 | 条件 | 语义 |
|---|---|---|---|
| P-18 | DOCUMENT / LIST | 无条件 | 登录用户可列出文档（行级过滤兜底） |
| P-24 | USER / LIST | admin 或 manager | 用户列表只对管理者开放 |
| P-38 | AUDIT / LIST | admin | 审计只对 admin 开放 |
| P-07 | POLICY / LIST | admin 或 manager | 策略列表对管理者开放 |

## 理由

1. **语义正确**：`READ` 回答"能不能看这一行"，`LIST` 回答"能不能进这个列表页"。
   混用会让策略作者被迫写 `resource.id == null` 这种技巧性条件
2. **放行列表 ≠ 放行数据**：列表接口本身不是敏感动作，敏感的是每一行。
   真正的边界在业务服务的行级过滤（ADR 0005），LIST 只挡"整个域都不该进"的人
3. **失败模式友好**：漏配 LIST 策略的现象是"列表页 403"（立刻被发现、影响面小）；
   若为了让列表能过而放宽 READ，现象是"所有人能看到所有行的存在"（静默越权）

## 为什么不给所有域无条件放行 LIST

USER / AUDIT / POLICY 这类域，光是"存在哪些用户 / 有哪些审计记录"本身就是信息。
所以 LIST 策略按域收紧：文档域无条件（行级过滤兜底），其余按角色收。

## 备选方案

- **让网关跳过集合请求不做策略门禁**：最简单，但等于放弃边缘这道闸，
  且"哪些路径算集合"要在网关硬编码，与 PDP 的策略割裂
- **给集合请求注入伪资源属性**（如 `id = "*"`）：策略里到处写 `resource.id == '*' || ...`，
  污染每条策略
- **只靠业务服务行级过滤**：能工作，但每个请求都已经打到业务服务了，
  网关的边缘拦截价值消失（也浪费一次下游调用）
